# reminder-server 改善設計

作成日: 2026-10-02

状態: 会話内の全体案は承認済み。この設計書のレビューと承認を経て実装計画を作成する。製品コード、依存関係、運用設定の変更は未着手。

監査資料: [リポジトリ監査](../../repository-audit-2026-10-02.md)

## 1. 目的と合意事項

WebPageReminder用の保存サーバーで、誤った入力、端末間の更新競合、保存や証明書更新の失敗によるデータ喪失・利用不能を防ぐ。利用者と運用者が、成功・競合・障害の状態と対処を判断できるようにする。監査で挙げた改善点を対応表に沿って修正し、設定、検証、文書を実装と一致させる。

ユーザーが承認した方針は次のとおり。

- 永続化をJSONファイルからSQLiteへ変更する。
- JSON内のBASE64画像はデコードし、元の画像バイト列をBLOBで保持する。
- HTTP APIはJSONを継続し、画像をBASE64で返す。
- 一覧全体の置換を、所有者認証と更新バージョンを持つ項目単位のAPIへ変更する。
- Expressを維持する。SQLite処理は同じNode.jsプロセス内の専用ワーカースレッドに分離し、ドライバーはbetter-sqlite3を採用する。
- API、認証、移行、運用、依存関係、ビルド、CI、ルート配下の指示・ガード・文書を整備する。
- 文書整備にCLAUDE.mdの新規作成を含める。
- .devcontainer配下のファイルは一切変更しない。

単一ホスト・単一アプリインスタンスで運用するサービスを前提とする。これは現行構成に基づく設計上の前提で、利用人数や性能の実測結果を意味しない。

成功条件は、既存データと画像の移行、項目単位の競合検出、明確なAPI契約、安全な起動・更新・終了、バックアップからの復元、監査項目との対応、文書と実装の一致である。クライアントのソースはこのリポジトリに含まれないため、クライアント変更は移行仕様と手順を提供する範囲とする。

## 2. 対象範囲と選択理由

### 採用する構成

Express、TypeScript、CommonJSを維持し、保存処理、HTTP契約、起動ライフサイクルを分離する。SQLiteはローカルの永続ディレクトリに配置する。ワーカーは1つ、HTTP処理用のDB接続は1つとし、操作を順番に処理する。HTTP側からはPromiseを返す保存インターフェースを使用する。

better-sqlite3は同期APIと関数単位のトランザクションを持ち、更新確認と複数テーブルの保存を短い処理にまとめやすい。npmのsqlite3は公式リポジトリに保守停止・非推奨が明記されているため新規採用しない。ドライバー自身のベンチマークをこのサービスの性能保証には使用しない。

### 比較した案

| 案 | 判断 |
| --- | --- |
| JSON保存と旧APIを補修する | 部分的な改善は可能だが、全件上書き、移行、認証、耐久性の問題を別々に抱える。今回の合意と一致しない |
| SQLiteをメインスレッドで使う | 小さなクエリには合理的だが、同期DB処理がHTTP受付を止める。画像処理を含む今回の境界には専用ワーカーを採用する |
| SQLiteを専用ワーカーで使う | 通信・終了管理が増えるが、同期DB処理とHTTP受付を分離できる。今回採用する |

Node.js標準のnode:sqliteも候補になり得るが、確認時点のNode.js 24ではRelease CandidateのAPIである。今回はbetter-sqlite3を使用し、ネイティブ依存の配布・更新をCIで検証する。

### 対象外

- .devcontainer内のNode、firewall、第三者proxy、初期化処理、拡張機能、設定の変更。
- クライアントの実装、ユーザー登録画面、Web管理画面、外部認証サービス。
- 複数アプリインスタンスからの書き込み、ネットワークファイルシステム上のDB、分散ジョブ処理。
- ORM、ESM化、フレームワーク変更、マイクロサービス化だけを目的とする刷新。
- 削除取り消しUIや削除データを保持する復元API。通常の削除は画像・内容を削除し、バックアップからの復元は運用機能とする。

監査B01/B02/B03/B06を採用する。B04は日時契約を採用し、削除取り消し機能は追加しない。B05は直接TLSを安全に維持する代替案で対応する。B01〜B06は設計候補であり、F01〜F32の指摘と同じ扱いで機能を無条件に追加するものではない。

## 3. コンポーネントとデータの流れ

| コンポーネント | 責務と依存 |
| --- | --- |
| 設定読み込み | 環境変数の解析、既定値、相互条件の検証。失敗時は設定名と理由を返し、秘密値を出力しない |
| Expressアプリ生成 | 認証、CORS、上限、検証、ルーティング、エラー応答。設定と保存インターフェースを受け取り、listenの副作用を持たない |
| 保存クライアント | ワーカー起動、依頼ID、待ち行列、応答との対応、終了。生SQLではなく型のある操作を送る |
| DBワーカー | DB接続、スキーマ更新、所有者・トークン確認、項目・画像操作、競合検出。CLIとDB操作の実装を共有する |
| サーバー起動 | HTTP/HTTPSサーバー生成、TLS更新、ヘルス、シグナル、リソース終了 |
| 管理CLI | 所有者・トークンの管理、JSON移行、バックアップ・復元・整合性検査。HTTPによる管理APIは提供しない |

更新リクエストは「アクセス境界の確認 → 認証 → JSON解析 → スキーマ検証 → DB操作 → JSON応答」の順に進む。TLS、DB接続、ワーカー、各待ち行列をルーティングの中で作成しない。

画像のデコード・エンコードはDBワーカー側で行い、メインスレッドへの画像メッセージはサイズ制限されたBASE64文字列とする。HTTPのJSON解析・シリアライズ自体はメインスレッドに残るため、ワーカー化だけで全ての負荷を除去できるとは扱わない。

## 4. SQLiteとスキーマ

永続先はDATABASE_PATHで指定し、既定値は./data/reminders.sqliteとする。初回起動は親ディレクトリと新しいDBを作成する。既存パスがディレクトリ、不明なスキーマ、壊れたDB、書き込み不能である場合は、置換や空DBへのフォールバックをせず起動失敗とする。

| テーブル | 主な内容 |
| --- | --- |
| schema_migrations | 適用済みスキーマのバージョン |
| owners | 所有者ID、管理用の表示名、作成時刻 |
| access_tokens | トークンハッシュ、所有者ID、作成時刻、失効時刻。平文トークンは保存しない |
| reminders | 所有者IDと項目IDの複合主キー、URL、タイトル、日時、各フラグ、作成・更新時刻、revision |
| reminder_images | 対応する所有者ID・項目ID、BLOB、MIME、BASE64またはdata URLというAPI上の形式 |
| deleted_reminders | 所有者ID・項目ID、最終revision、削除時刻。削除済みIDの再利用を防ぐ。タイトル、URL、画像は残さない |

JSON文書をそのまま1カラムに保存する方式にはしない。所有者と項目の制約、画像の外部キー、型・NOT NULL・CHECK制約、必要な索引をDBにも設ける。外部キーを有効化し、真偽値は0/1、日時はUTCの正規化された文字列として保存する。

WALを使用し、同期設定は耐久性を優先するFULLとする。DBロック待ちは2秒を上限とし、通常のHTTP操作はワーカーの1接続で行う。管理CLIの所有者・トークン操作だけは短い専用トランザクションを許可し、SQLiteの書き込み直列化と同じロック待ち上限に従う。CLI接続を処理後に閉じ、独立した長期書き込みプロセスを追加しない。稼働中の.dbファイルだけをコピーするバックアップは認めない。設定値だけで、媒体故障や全てのファイルシステム障害を防げるとは説明しない。

スキーマ更新はバージョン管理されたトランザクションとして適用する。現在のコードより新しいDBバージョンは起動拒否し、破壊的なスキーマ更新の前にはバックアップを必要とする。JSON取り込み・復元・スキーマ更新はサーバー停止中にのみ行う。稼働中の管理CLIは既存スキーマの適合を検証し、スキーマ変更を実行しない。

## 5. DBワーカーの動作

- 起動時にDB初期化を完了してからHTTP受付を開始する。ワーカー準備待ちは10秒を上限とする。
- 依頼は操作名、依頼ID、検証済みパラメーターを持つ。HTTPリクエストのSQL文字列を受け取らない。
- 実行中1件に加え、待機中は最大32件とする。待機が5秒を超えた依頼は開始前に失敗させる。容量超過は503を返す。
- 更新バージョンの確認と書き込みは同じトランザクションで実行する。トランザクション内でawaitやHTTP通信を行わない。
- ワーカーのエラー・異常終了時は待機中のPromiseを残さず失敗させ、readinessを失敗にする。終了手順を開始し、再起動はプロセス管理側に委ねる。
- 異常終了した書き込みのコミット有無は不明になり得る。アプリ内部で無条件に再送せず、クライアントは再取得して状態を確認する。
- 終了は新規依頼の停止、受け付け済み処理の完了、接続終了、ワーカー終了の順に行う。

この構成はHTTP受付の応答性を保つためのもので、SQLiteの書き込みを並列化するためのものではない。性能・メモリの測定では、ワーカー通信と画像のJSON処理も含める。

## 6. 所有者認証と接続境界

管理CLIで所有者を作成し、十分な乱数を使用したトークンを発行する。APIはAuthorization: Bearerを使用し、認証結果から所有者IDを決定する。HTTP入力のkeyやownerIdを保存範囲の指定に使用しない。

DBにはトークンのSHA-256ハッシュのみを保存する。トークンは高エントロピーの乱数であり、利用者が選ぶパスワードを同じ方式で保存する機能は提供しない。所有者ごとに複数トークンの発行と個別失効を可能にし、ローテーション時には新規発行後に旧トークンを失効させる。所有者作成・トークン発行・失効はCLI経由のみとする。

トークンの平文表示は発行操作の結果として一度だけ行う。既存トークンの再表示、ログ出力、CLI引数による既存トークンの受け渡しを避ける。HTTPログにもAuthorization、本文、画像、移行キーを含めない。

毎リクエストのALLOW_DOMAIN名前解決とlocalhost判定を廃止する。既定の追加IP制限はなしとし、任意のALLOWED_IPSに明示されたIPv4/IPv6のリテラルだけを許可できるようにする。IPv4-mapped IPv6を正規化して比較する。旧ALLOW_DOMAINが設定されている場合は、黙って無効にせず設定移行エラーを返す。

trust proxyは既定で無効とする。プロキシを使う場合だけ、TRUSTED_PROXIESに信頼するIP/CIDRを明示し、無条件にtrueや任意のX-Forwarded-Forを信頼しない。認証、追加IP制限、制限用の接続元判定をJSON解析より前に行う。CORSのpreflightとヘルス確認は別の契約で扱う。

レート制限はプロセス内で実施し、認証前は接続元ごとに1分120リクエスト、認証後は所有者ごとに1分120リクエストを既定値とする。429とRetry-Afterを返す。管理用ヘルス確認はこのカウントから除外する。制限記録には有効期限と上限を設け、接続元の増加で無制限にメモリを使用しない。

## 7. v2 APIと破壊的変更

旧POST/PUT /remindersは410 Goneと移行先を含むJSONエラーを返し、旧保存処理を実行しない。大きな旧本文を解析する前に応答する。旧HTTP APIの互換レイヤーは提供しない。

| メソッド・パス | 動作 |
| --- | --- |
| GET /v2/reminders | 認証した所有者の一覧。空の場合も200とitems: []を返す |
| GET /v2/reminders/:id | 1件取得。ETagとrevisionを返す |
| POST /v2/reminders | クライアントが指定したidで1件作成。201と作成結果、Location、ETagを返す |
| PATCH /v2/reminders/:id | 指定フィールドだけ更新。If-Matchによるrevision照合が必須。200と更新結果、ETagを返す |
| DELETE /v2/reminders/:id | If-Matchが必須。内容と画像を削除し、削除記録を保存する。200とid・deleted: true・更新後revisionを返す |
| GET /healthz | プロセスのHTTP応答確認。秘密情報を含まない |
| GET /readyz | DB準備完了・処理可能状態と終了状態を確認。利用不能時は503 |

### 項目と競合

API項目は既存のid、url、title、thumbnail、reminderTime、autoOpen、webPush、createdAt、hiddenを維持し、thumbnailMime、updatedAt、revisionを追加する。新規作成のcreatedAtとupdatedAtはサーバーが決定する。画像なしはthumbnail: ""、thumbnailMime: nullで表現する。作成時に必要な入力はid、url、title、thumbnail、reminderTime、autoOpen、webPush、hiddenとし、画像に応じてthumbnailMimeを使用する。

revisionは1から始まり、成功した変更ごとに増える。ETagは引用符で囲まれたrevisionとする。PATCH/DELETEは単一の強いETagをIf-Matchに指定する契約とし、ワイルドカードや複数候補は受け付けない。PATCHに変更可能なフィールドが1つもない場合は422とする。id、所有者、createdAt、updatedAt、revisionの書き換えや未知のフィールドは拒否する。

同じ所有者・同じIDへの二重作成は409とし、重複したレコードは生成しない。削除済みIDも再利用を拒否する。新規項目は新しいIDを使う。これにより古い端末の再送が削除した項目を復活させない。別所有者のIDを指定しても存在確認できないよう、自分の項目がない場合と同じ404を返す。

If-Match欠落は428、不一致は412、存在しない項目は404とする。競合応答はエラーコードと再取得の案内を返し、古い入力を自動マージしない。クライアントは現在値を取得して利用者の変更を再適用する。通信失敗で結果が不明な作成は指定IDを取得して確認でき、更新・削除も再取得後に判断する。

### 一覧

一覧はitemsとnextCursorを持つJSONオブジェクトとする。既定20件、最大50件で、createdAtとidの安定した順序によるカーソルページングを使用する。日時が同じ項目でも取りこぼさないよう両方をカーソルに含める。カーソルは入力検証し、所有者条件は必ず認証から付加する。

一覧は複数ページ全体のスナップショットを保証しない。同時変更中は再取得が必要になり得るが、一覧を再保存するAPIがないため、その読み取りだけで変更が失われることはない。増分同期、長期間保持する同期トークン、ページングをまたぐDBトランザクションは追加しない。

### HTTPとエラー

本文を持つ操作はapplication/jsonのみ受け付け、他の形式は415、壊れたJSONは400、スキーマ違反は422、上限超過は413とする。認証不備は401とWWW-Authenticate、追加IP制限の拒否は403とする。APIの成功・失敗はapplication/jsonで返す。OPTIONSの成功は本文なしの204を例外とする。

エラー本文はerror.code、error.message、必要に応じたフィールド名、requestIdを持つ。本文の入力値や秘密値、SQL、スタックトレースを返さない。予期しないエラーは500、DBロック・過負荷・終了中など一時的な利用不能は503として区別する。

認証された応答はCache-Control: no-storeとする。リクエストIDはサーバー側で生成し、ログと応答を対応づける。

## 8. 入力・画像・容量の契約

- 入力オブジェクトはスキーマ検証し、型の強制変換をしない。文字列のtrueや数字、配列を真偽値・所有者・IDとして受け入れない。
- idは空でない制御文字なしの文字列で最大128文字。URLやファイルパスとして使用せず、DBの値としてパラメーター化する。ルートへ指定するときはクライアントがURLエンコードする。
- URLはhttp/httpsのみ、最大4096文字。タイトルは最大1024文字。サーバーはURLを取得しない。
- reminderTimeは実在する日時を表すISO 8601で、Zまたは明示的なUTCオフセットが必須。UTCに正規化する。過去の項目を移行・表示できるよう、過去の日時という理由では拒否しない。
- autoOpen、webPush、hiddenは真偽値。実行・通知機能はクライアントの責務であり、このサーバーに通知処理を追加しない。
- BASE64とdata URLを受け付け、曖昧な文字列を寛容なデコードだけで受理しない。形式を検証して元のバイト列を保存する。再圧縮、リサイズ、画像形式の変換は行わない。
- MIMEはdata URLの宣言、検出可能な画像形式、明示されたthumbnailMimeの整合性を確認する。未判定形式ではthumbnailMimeの明示を必要とする。画像をDBから直接HTMLとして配信するエンドポイントは作らない。
- API上のBASE64単体またはdata URLという形式は保存して返す。BASE64文字列の改行等を正規化する場合も、デコード後の画像バイト列は変えない。

次の制限は既定値で、正の整数として設定変更を認める。値を設定するだけで既存データを切り詰めない。

| 設定 | 既定値 |
| --- | --- |
| MAX_JSON_BYTES | 2 MiB |
| MAX_IMAGE_BYTES | デコード後1 MiB/項目 |
| MAX_REMINDERS_PER_OWNER | 有効な項目1000件/所有者 |
| MAX_IMAGE_BYTES_PER_OWNER | デコード後の画像合計128 MiB/所有者 |

MAX_JSON_BYTESは画像のBASE64展開とメタデータを収容できる値であることを設定検証する。所有者単位の件数・画像容量判定は、同時更新で上限を超えないよう保存トランザクション内で行う。削除済みIDの軽量記録は有効項目数には含めず、保持によるDB増加は運用上の制約として記載する。

## 9. CORS

ALLOWED_ORIGINSはカンマ区切りの完全なorigin一覧とする。既定は空で、ブラウザーからのクロスオリジン利用には明示設定が必要である。任意のlocalhost類似ホスト名、正規表現、ワイルドカード、null originを自動許可しない。

許可したoriginだけを返し、Vary: Originを付ける。GET、POST、PATCH、DELETE、OPTIONSを許可し、Authorization、Content-Type、If-Matchを許可ヘッダーに含める。ETag、Location、X-Request-Idを公開する。Cookie認証を使わないためAccess-Control-Allow-Credentialsは有効化しない。

preflightはJSON解析・Bearer認証なしで設定を確認し、許可する場合は204、未許可の場合は403とする。OriginなしのCLI・クライアントリクエストはBearer認証で扱う。CORSを認証やアクセス境界の代替にはしない。

## 10. 既存JSONの取り込みと切り戻し

通常起動で旧JSONを自動変換しない。旧ファイルの場所と所有者対応表を明示する管理CLIのimport-json操作を提供する。旧STORAGE_FILEが設定されている場合は、JSON移行を案内する設定エラーとし、値をSQLiteパスと誤認しない。

移行手順は次の順序とする。

1. 旧サーバーを停止し、原本JSONと旧設定を別の安全な場所に保全する。
2. CLIの検証モードで、構文、own propertyのキー、一覧、IDの重複、必須値、日時、画像、容量を検査する。
3. 旧keyと既存の所有者IDの対応表を指定する。各keyを別所有者へ対応づけ、空一覧の所有者も保持する。keyからトークンを作ったり、keyを認証に流用したりしない。
4. 取り込み先所有者に既存項目・削除記録がある場合は拒否する。対象所有者全体を単一トランザクションで取り込み、失敗時は全件ロールバックする。
5. 項目数、ID、各値、UTCへの時刻変換の一致と、画像バイト列のハッシュ一致を検証する。
6. バックアップを作成し、v2対応クライアントと認証トークンを設定して切り替える。

JSON原本は読み取りのみで使用し、上書き、移動、削除をしない。エラー報告は位置・項目番号・フィールド名・理由を示し、画像、トークン、旧key、URLやタイトルなどの内容を出力しない。不正な項目を黙って飛ばさない。日時にオフセットがない、MIMEが判定できない、上限を超える等の場合は中止し、修正した作業用コピー・明示された画像MIME・容量設定を用いて再実行する。曖昧な日時をサーバーのローカル時刻として推測しない。

createdAtとIDは旧値を保持する。時刻は同じ瞬間を示すUTCへ正規化し、初期updatedAtはcreatedAt、revisionは1とする。通常の作成でサーバーがcreatedAtを決定する契約と、管理移行で旧値を保持する契約を分ける。

SQLiteと旧JSONの二重書き込みはしない。切り戻しは新サーバーへの書き込み開始前までなら保全した旧JSONと旧サーバーを使用できる。新しい書き込み開始後に旧JSONへ戻すと新しい変更を失うため、通常の復旧はSQLiteバックアップから行う。旧形式への自動逆変換は提供しない。

## 11. バックアップ・復元

バックアップは同じホストの管理CLIがSQLiteバックアップAPIで整合性のある別DBを作る。稼働中はCLIが既存DBを読み取り専用で開き、アプリの書き込み接続を追加しない。CLIはこの接続でスキーマ更新や所有者管理を行わず、バックアップ終了後に閉じる。書き込みの継続によりバックアップが進まない場合に備えて、作成の猶予は60秒とし、失敗を明示する。停止中も同じバックアップ操作を使用できる。専用HTTP管理APIやIPCサービスは追加しない。

バックアップは既存ファイルを上書きせず、同じディレクトリ内の一時ファイルへ作成し、整合性検査後に確定名へ変更する。失敗したファイルを成功したバックアップとして残さない。DB・バックアップには画像と認証ハッシュが含まれるため、アクセス権を制限する。

復元はサーバー停止中に実施する。対象DB、WAL、SHMを安全に退避し、バックアップのスキーマバージョン、integrity_check、foreign_key_checkを確認する。稼働中ファイルの上書きや、新DBに旧WALを組み合わせる復元をしない。復元後に項目・画像・認証・readinessを検証する。バックアップ以後の変更とトークン失効状態も巻き戻ることを運用手順に明記する。

保持・別媒体へのコピーは運用者の責務とし、CLIは暗黙の自動削除をしない。

## 12. 起動設定、TLS、ログ、終了

### 起動設定

Node.js 24 LTSの実装時点で更新済みのパッチを使用し、packageのengines、CI、本番Docker、READMEを揃える。.devcontainerのNodeは変更しない。PORTは既定3000で、1〜65535の整数だけを認める。HOSTはローカル起動で既定127.0.0.1、コンテナ内では明示して0.0.0.0とする。HTTPのヘッダー受信上限時間は15秒、リクエスト受信は30秒、keep-aliveのアイドル時間は5秒とする。

TLS_MODEはdirectまたはoffとする。productionの既定はdirect、development/testはoffとする。directはCERT_PATH内のfullchain.pemとprivkey.pemを必要とする。productionでoffを指定できるのは、loopback待受または明示的な信頼済みプロキシ構成を設定した場合とし、設定検証と文書で条件を示す。

FRONTEND_ORIGIN、ALLOW_DOMAIN、STORAGE_FILEなど旧設定は移行メッセージで検出し、黙って無視しない。.env.exampleには値を含まない説明と開発用の非秘密設定だけを置く。

### TLS

fullchain.pemとprivkey.pemを一組として読み込み、鍵と証明書の組み合わせを検証してから適用する。初回の読み取り・検証失敗は起動失敗とする。更新はHTTPSサーバーのsetSecureContextで行い、待受ソケットの閉鎖や再生成を伴わない。

監視はファイルの変更・追加・置換と監視エラーを扱い、連続イベントをまとめる。読み込み中に更新イベントが来た場合は未処理状態を残し、終了後に最新版を再読込する。不完全なペアや読み取り失敗は現在の有効なTLSコンテキストを維持し、ログで報告する。失敗した再読込は最大3回、1秒間隔で再試行し、後続イベントも受け付ける。

Certbotのlive配下のsymlinkがarchive配下を参照することを考慮し、コンテナには参照先を含む証明書ディレクトリを読み取り専用でマウントする。非root実行ユーザーが鍵を読める権限設定を運用者が行い、鍵をworld-readableにする手順を推奨しない。

### ログとヘルス

ログは時刻、レベル、requestId、ルート、ステータス、処理時間、分類されたエラーコードを持つ構造化JSONとする。URLのクエリー、Authorization、本文、画像、設定の秘密値を記録しない。内部エラーの原因とスタックは機密値を除いて本番でも追跡できるようにする。

healthzはHTTP応答のみ、readyzはワーカー初期化・DB問い合わせ・終了状態を確認する。応答は最小限の状態で、DBパス、所有者、証明書、構成値を公開しない。ワーカー停止時と終了開始後のreadinessは503とする。

### 終了

SIGTERM/SIGINTではreadinessを失敗にし、新規受付を止める。受け付け済みHTTP処理を待ち、証明書監視とタイマー、DB接続、ワーカーを終了する。全体の終了猶予は10秒とする。期限を超えた場合は接続を終了し非正常終了として記録する。処理が正常終了した場合はexit code 0、初期化・ワーカー障害は非0で終了する。

## 13. ビルドと型・Lint

tsupを廃止し、通常のtscでsrcをdistへコンパイルする。相対importとnode:接頭辞を使用し、実行時に解決できない@/エイリアスを残さない。ソースマップを生成し、DBワーカー・CLIも成果物に含める。better-sqlite3などの実行依存はバンドルせず、本番node_modulesに含める。

package scriptsはdev、build、start、typecheck、lint、test、check、adminを持つ。startはビルド済みサーバー、devは開発起動、checkは型・lint・意味のあるテストを順に実行する。公開レジストリとロックファイルだけでnpm ciできる状態とし、GitHub認証やAIツールを通常起動の必須条件にしない。

strictに加えてnoUncheckedIndexedAccess、exactOptionalPropertyTypes、noImplicitReturnsを使用し、HTTP入力とワーカーメッセージを実行時にも検証する。型情報を使用するESLintでPromiseの未処理・型のない境界を検査する。Node globalsを設定し、dist、node_modules、生成物、.devcontainerを対象から除外する。

使用しないcookie-parser、debug、http-errors、greenlock関連型、tsup、alias専用依存などは実装上の使用を確認して削除する。依存更新は最新majorへの一括置換ではなく、対応Node、Express、型・Lint、ネイティブアドオンの組み合わせを検証する。ロックファイルを更新し、実行依存と開発依存の既知脆弱性を再確認する。

## 14. DockerとCI

Dockerはmulti-stageを維持し、npm ciでビルドと実行依存を用意する。builderとrunnerのNodeバージョン、OS、CPUアーキテクチャを一致させ、ネイティブアドオンを正しく配布する。必要なビルドツールはbuilderにだけ置く。ARCHの空の接頭辞ではなくDocker標準のplatform指定を使用する。

実行は非rootのnodeユーザーとし、書き込み可能なdataディレクトリを用意する。Composeは名前付きdataボリュームにDB、WAL、SHMをまとめて保持し、initと終了猶予を設定する。既定の資源上限はメモリ512 MiB、CPU 1、PID 128とし、運用に応じて変更できるよう記載する。restartはunless-stopped、終了猶予はアプリより長い15秒とする。

Composeの標準設定はdirect TLSとし、CERT_PATHと証明書マウント元を必須変数として、未設定なら明確な設定エラーとする。ローカルHTTPで試す手順はREADMEに別途示す。JSONファイルを通常の永続ボリュームとしてマウントしない。

.dockerignoreではGit情報、node_modules、dist、秘密設定、保存データ、バックアップ、証明書、.devcontainerを除外する。ベースイメージは確認済みタグとdigestで固定し、更新を継続する。

CIはpull_request、push、workflow_dispatchで実行する。型、lint、テスト、ビルド、実行依存の監査、コンテナ起動・終了・永続化・非root動作を検証する。Buildxで作ったイメージを再利用し、Composeで二重ビルドしない。直接TLSの起動・更新はテスト用証明書を一時領域で生成して検証し、本番秘密ファイルを使わない。

permissionsは必要最小限のcontents: readとし、外部Actionsを確認済みコミットSHAで固定する。Dependabotにnpm、GitHub Actions、ルートDockerを設定し、.devcontainerの更新は含めない。CIからデプロイ、イメージ公開、PRマージは行わない。

## 15. README、CLAUDE.md、秘密情報ガード

READMEは必要Node、npm ci、開発・本番起動、所有者とトークン管理、完全なAPI例、revision競合、画像形式、全設定、Docker権限、TLS、JSON移行、バックアップ・復元、制限を記載する。例は実際のスキーマを満たし、reminderTimeを使用する。HTTPとHTTPSの手順、旧APIからのクライアント変更を区別する。

ユーザー指定によりCLAUDE.mdを新規作成する。既存のAGENTS.mdはCLAUDE.mdを指すsymlinkを維持し、リンク切れを解消する。内容は次を含む。

- リポジトリの用途、実行環境、構成、HTTPとワーカーの責務。
- 開発・型・lint・テスト・ビルド・管理CLIのコマンドと必要な検証。
- 画像バイト列の保持、所有者境界、revision、トランザクション、移行の原本保全。
- .devcontainerを今回の変更対象から除外する制約と、そこで残る監査指摘。
- .env、.env.*、証明書、DB、バックアップの内容を無断で読み取り・出力しない規則。公開テンプレートとテストの模擬データは区別する。
- 特定ライブラリ・API・CLIの仕様確認には、ユーザー指定のContext7手順を使用する。libraryでID解決、docsで取得、質問ごと最大3コマンド、機密値を問い合わせない、ネットワークエラーとquotaエラーの対処を記載する。
- README、設計書、監査資料への参照。文書中に、未実装のコマンドを現在利用可能であるかのように記載しない。

ルート配下のClaude/Codex設定とシェルガードは、パス固定や秘密ファイル対象漏れを修正する。ツール入力のフィールド差、.env.actions、絶対・相対パス、引用符、パスの区切りを模擬データで検証する。正規表現のシェルガードを完全な隔離機構とは説明しない。

ClaudeとCodexのhook登録は、実装時点の公式に対応した形式を確認して整備する。Codexの対象バージョンで未対応の登録がある場合は動作すると表示せず削除し、実際に利用できる権限設定とCLAUDE.mdの指示に置き換える。秘密情報保護の可否をテキスト上の設定だけで保証しない。

追跡済み.env.actionsとreminders.jsonは内容を読み出さず、作業ファイルを保持してGitの追跡から外す。.env.*は公開テンプレートを除いてignoreし、SQLite、WAL、SHM、バックアップもignoreする。Git履歴の書き換え、秘密値の確認・出力、認証情報の自動ローテーションはこの作業に含めない。

## 16. 検証と受け入れ条件

意味のある振る舞い・故障境界を検証する。内部実装をそのままなぞるテストや、単純な文書変更のためのテストは追加しない。

| 対象 | 受け入れ条件 |
| --- | --- |
| 初回・設定 | 空環境でDBを初期化でき、未知の新しいスキーマ・壊れたDB・不正設定は起動拒否する |
| 所有者 | トークンなし・不正・失効は401、別所有者の読み書きはできない。旧keyは認証にならない |
| 入力 | 必須値欠落、型違い、未知フィールド、特殊ID、曖昧・不正日時、壊れたBASE64、MIME不一致を検査し、失敗時に保存を変更しない |
| 競合 | 同じrevisionの同時更新は1件だけ成功し、他は412。別項目の更新は保持する。削除後の再送・同じIDの作成で復活しない |
| 上限 | 認証前に大きな本文を解析しない。本文・画像・件数・所有者容量・レート・ワーカー待ち行列の境界を検証する |
| HTTP | 空一覧、ページング、Content-Type、エラーコード、CORS、Vary、204、ETag、If-Match、旧APIの410を実リクエストで確認する |
| SQLite | 中途失敗のロールバック、所有者制約、画像との原子性、ロック時の失敗分類を確認する |
| 移行 | 合成した旧形式の複数所有者、空一覧、特殊キー、画像を移行する。不正項目で全体ロールバックし、原本が変わらず、値と画像のバイト列が一致する |
| バックアップ | 稼働中の読み取り専用接続からの整合したバックアップ、期限超過、上書き拒否、停止中の復元、画像と認証の復元を確認する |
| TLS | fullchainによる接続、連続更新、不完全な鍵ペア、監視エラーで待受を維持し、最後の有効な更新を適用する |
| 終了・ヘルス | ワーカー障害でpending処理が残らず、readinessが503になる。SIGTERMで処理を待ち、監視・DB・ワーカーが終了する |
| 配布 | npm ci、型、lint、テスト、tscビルド、成果物からの起動、ネイティブ依存、本番非rootコンテナ、再起動後の永続化を確認する |
| 文書・ガード | AGENTS.mdがCLAUDE.mdを参照でき、例と設定が実装に一致する。秘密ファイルガードは秘密を含まない模擬入力で検証する |
| 除外範囲 | git diffで.devcontainer配下の変更がない |

新しい依存・運用設定に合わせてnpm auditを再実行し、監査時の脆弱性が残っていないことを確認する。外部の新しいAdvisoryや実行環境の未対応により検証できない事項は、成功扱いにせず結果と制約を記載する。Dockerなどがローカルで使えない場合は、ローカル未実行とCIで実行する項目を明示する。

負荷確認は、同時の小さなリクエストと上限近くの画像処理を組み合わせ、応答時間とメモリの増加を記録する。未測定のスループットやレイテンシの保証値を設定しない。
