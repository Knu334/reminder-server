# Restored-data verification and recovery

These commands validate a separately restored environment. They do not perform PITR, recreate Cognito pools or users, implicitly publish a gate, change deployed table references, enable a schedule, or apply Terraform. The implementation and tests used synthetic data and SDK transports; no actual PITR rehearsal or AWS recovery operation was performed.

1. Stop API writes and the cleanup schedule through a separately authorized deployment operation. Keep them stopped throughout recovery and final verification. Select one consistent recovery point and restore **all three** DynamoDB tables: reminders, owner_state, and image_jobs. Use three new table names, distinct from each other and from every live table name. Restore the runtime keys and the image_jobs `cleanup_by_due` GSI (KEYS_ONLY), including the existing sparse cleanup attributes. Preserve the live tables and original S3 versions unchanged. DynamoDB PITR retention is 35 days; the image lifecycle retains noncurrent versions for 60 days. Preserve referenced old image versions before that lifecycle can remove them.
2. Create two private configuration JSON files in the same format as [migration configuration](migration.md). `--source-config` must contain the actual currently deployed account, region and resource references; `--restored-config` must name the isolated, unpublished restored tables and original production image bucket. Both files include `accountId`, `region`, `remindersTable`, `ownerStateTable`, `imageJobsTable`, `imagesBucket`, `issuer`, `clientId`, `expectedApiId`, `expectedStage`, and optional `sourceIps`/`limits`. Account, region and image bucket must agree. The supported activation keeps the existing API ID/stage and current Cognito issuer/client/domain; restoring or migrating a pool or bucket is outside this cutover. The scripts compare STS GetCallerIdentity with the explicit account and never discover resources by name. Use short-lived credentials through the normal SDK provider. Confirm the restored table names are absent from active deployed configuration before running anything.
3. In the Cognito console, confirm the **current** issuer and actual `sub` for every intended recovered owner, including owners with zero items. Store a private JSON array in `--owner-identities`: `[{ "ownerId": "<SHA-256 owner ID>", "issuer": "<current issuer>", "sub": "<console-confirmed subject>" }]`. Include exactly the intended final restored owners. `ownerId` is the runtime SHA-256 of UTF-8 JSON `[issuer, sub]`. No username or email search, account creation, or inference occurs. If an old recovered owner is supplied with a recreated user's new subject, verification reports a mismatch; a recreated username cannot acquire its old data automatically. **DynamoDB PITR does not restore Cognito passwords or sessions**; every report contains `cognitoCredentialsRestored: false`.
4. Choose a lowercase UUID and retain the exact private inputs and run ID. Default verification is read-only, including recovery metadata and the publication gate:

   ```sh
   npm run recovery:verify -- --source-config /private/live.json --restored-config /private/restored.json --owner-identities /private/current-owners.json --run-id <uuid>
   ```

   A restored owner_state table can retain the old `published: true` gate. Default verification rejects it. After confirming the isolated target, explicitly prepare only that restored gate:

   ```sh
   npm run recovery:verify -- --source-config /private/live.json --restored-config /private/restored.json --owner-identities /private/current-owners.json --run-id <uuid> --prepare-restored
   ```

   Preparation conditionally sets `GLOBAL/PUBLICATION` to `{ published: false, runId }`, creating the row only if absent. The gate remains false through every recovery write and failure. A prepare-only invocation can still exit 2 when data needs preservation or explicit owner mapping; it never means the environment was published.
5. Verification reads every restored item, exact owner `STORAGE.itemCount`/`imageBytes` counters, every image job, and every referenced pinned image. Deleted records do not count as active items. Empty owners require zero counters and a current confirmed identity. It checks runtime record validation, job ownership/key/version/MIME/bytes/SHA-256, committed jobs without cleanup attributes, sparse cleanup keys on other job states, and orphan committed jobs. It checks original bytes and current restored S3 versions; a valid source object cannot hide a corrupt restored current object. Missing versions, checksum failures, counters, owner mismatches, unfinished remaps, invalid jobs, unreadable pages, or insufficient budget block readiness. Different requested run IDs cannot conceal an unfinished owner remap already present in the restored tables. Diagnostics contain positions, fixed field names and reasons, without IDs, URLs, titles, image bytes, issuer/sub or credentials. Exit 0 means `readyToSwitch: true`; exit 2 means a mismatch or failure. Strong reads are paginated, not a multi-table snapshot: keep administrative and application writes disabled.
6. Explicitly preserve noncurrent referenced images:

   ```sh
   npm run recovery:verify -- --source-config /private/live.json --restored-config /private/restored.json --owner-identities /private/current-owners.json --run-id <uuid> --preserve-images
   ```

   A pinned GET validates original version, MIME, length, checksum and bytes. A durable restored-only pending job and image intent reserve a **new UUID and new `images/<ownerId>/<UUID>` key before Put**. The original bytes are uploaded with `IfNoneMatch: "*"` and unchanged MIME/length/SHA-256. A pinned GET and current HEAD validate the result before a conditional restored-table transaction changes the reminder reference, commits the new job, and completes the old restored job. IDs, timestamps, revision, fields, and owner counters remain intact. Original S3 keys/versions and live jobs are never rewritten or deleted; migration's deterministic stable keys are never reused as upload destinations. Stored historical image bytes are preserved independently of a smaller current per-image admission limit.

   If interrupted before or after Put, rerun with the same inputs and UUID. The saved intent selects the same new key. HEAD and pinned GET compare the existing version against original bytes before another conditional Put is considered; mismatches or a delete marker abort. A newly chosen UUID cannot adopt a preexisting object even if its checksum matches. Completed references are verified and skipped. Failed runs stay unpublished; never delete progress to force a different upload key.
7. If ownership must change, supply a separate private explicit array: `[{ "oldIssuer": "<historical issuer>", "oldSub": "<historical subject>", "newIssuer": "<current issuer>", "newSub": "<current subject>" }]`:

   ```sh
   npm run recovery:verify -- --source-config /private/live.json --restored-config /private/restored.json --owner-identities /private/current-owners.json --run-id <uuid> --owner-map /private/explicit-map.json
   ```

   The historical issuer/sub is authoritative only when its hash identifies the old restored owner. It can differ from today's source-config issuer after a pool was recreated. The new issuer must match the restored configuration and the console-confirmed identity file must include its new owner hash. Map one old owner to one distinct, unused new owner. Duplicate targets, merges, mapping cycles, existing target records/storage/jobs and quota violations are rejected before **any** mapped owner's image is copied. Target limits default to 1000 active items and 128 MiB image bytes per owner; explicit effective limits govern the aggregate preflight.

   For each owner, persist its bounded per-item manifest and counts/hash, then copy reminders (including tombstones) to the new owner partition. Referenced images use the same durable pipeline with new target-owner keys. Each new reminder, committed image job and exact target counters commit atomically. Reverify all target fields, images/jobs, record count and counters before deleting old restored records. Repeat that full check when resuming cleanup after a failure. Old restored counters decrement atomically with each removal and old restored image jobs become done; the zero old storage row is removed only after completion. Live records and source image versions remain unchanged. Remapping never publishes, changes URLs or touches Cognito credentials. `--preserve-images` may accompany `--owner-map`; remapping runs first and the final preservation/verification pass checks the resulting owners.
8. Perform the bounded cutover below. Default verification and prepare/preserve/remap never publish. Only the explicit, separate `--publish-restored` mode publishes the prepared restored gate after fresh verification. It cannot be combined with prepare, preservation or owner mapping.
9. Retain private run notes, receipts and original recovery inputs until acceptance. Clean up abandoned temporary restored tables and unused recovery image copies only through a separately planned operation after proving they are not referenced; this CLI performs no resource cleanup. Do not remove retained source versions or live tables as part of recovery verification.

Recovery of Terraform state restores infrastructure management metadata, not application data. Rolling back an application ZIP changes code, not DynamoDB items or S3 versions. PITR/data recovery uses new tables and preserved image versions; after new writes, returning to an earlier data snapshot requires its own reconciliation plan. These operations are separate and must not be substituted for one another.

## Reviewed same-account cutover and rollback

This is an operator procedure; none of these AWS operations was executed during implementation. Keep one private evidence packet with the recovery point, exact original and restored identities, console-confirmed owners, fresh read-only report, recovery UUID, table schema/protection proof, known API/Cognito baseline, selected immutable commit, registered ZIP key/version/checksum and saved-plan review/custody digests. Never put it in Git or public logs.

1. Quiesce **all** application writes and traffic, all administrative/import/recovery writers, and cleanup. Use a normal reviewed application release to set `scheduler_enabled=false` and `allowed_source_ips=["<dedicated operator egress IP>"]` first; retain that exact allowlist through the cutover previews and apply. Confirm a request from every ordinary client egress is denied and no ordinary client shares the operator egress. Allow only the operator to access the API and perform no writes. Drain in-flight API invocations (10-second timeout), stop administrative/direct cleanup invocation, and let queued Scheduler/Lambda retries drain or expire before switching grants (each has3600-second maximum event age; cleanup timeout660 seconds). Verify actual queue/invocation cessation rather than assuming Scheduler disable cancels in-flight work. Keep other writers stopped throughout. The original published gate alone is not a maintenance fence. If an exclusive operator egress and verified drain cannot be established, stop before the transition. No maintenance/admin CLI or workflow is supplied here.
2. Restore/prepare/preserve/remap using steps1–7. In the same account/region, confirm restored table names are 3–64 ASCII letters/digits/underscore/dot/hyphen, all distinct and disjoint from **every** original table name. Confirm exact string keys, the KEYS_ONLY `cleanup_by_due` index, PAY_PER_REQUEST, deletion protection, PITR35 and owner-state `expiresAt` TTL. Configure those protections through the separately authorized restore operator before selection; PITR does not necessarily inherit every setting. Keep original managed tables and original bucket/versions retained. A fresh read-only verification must return readyToSwitch=true after copies are current.
3. Privately review the exact selection (JSON uses the same keys in every root):

   ```json
   {"restored_tables":{"reminders":"<reviewed-restored-reminders>","owner_state":"<reviewed-restored-owner-state>","image_jobs":"<reviewed-restored-image-jobs>"}}
   ```

   Empty `{}` selects originals. A partial map, original-name alias, duplicate, wildcard or arbitrary ARN is rejected. The name bound keeps IAM policy size finite. Account/region/prefix and image bucket remain unchanged. No ordinary GitHub role may change bootstrap trusts, boundaries or ceilings.
4. With the service quiesced, the bootstrap operator first reviews and applies a **saved bootstrap plan** with this exact `restored_tables` map and unchanged repository/OIDC/API inputs. Check that runtime ceilings now authorize only the selected three tables and their exact cleanup index; metadata-only delivery reads cover original plus selected ARNs, and original control-plane management grants stay scoped to originals. This deliberately removes runtime access to originals during the cutover. Reject wildcard/data-plane delivery grants, role-trust changes and unexpected resources. Retain the prior bootstrap inputs for rollback.
5. Set the identical map in `PLATFORM_INPUTS_JSON`, keep the known Cognito baseline, and use the existing platform preview→review→apply sequence. The platform reads/verifies restored tables without adopting them, retains all three original managed/deletion-protected tables, updates runtime grants and selects its existing name/ARN outputs. Review names/ARNs plus the `restored_tables` output and unchanged original bucket/Cognito outputs. Stop if any restore validation or post-apply identity check fails. Reverting table selection never destroys originals or restored resources.
6. Set the same map explicitly in `APPLICATION_INPUTS_JSON` (the driver also derives it from verified platform outputs and rejects disagreement). Run a fresh application preview using the exact known API/Cognito baseline, `operator_api_seed=false`, `scheduler_enabled=false`, `published=false`, and the selected registered ZIP/version. Review all three table names in `inputs.json`, `platform-outputs.json`, **both** Lambda environments, and `runtime_data`; verify original bucket, region, `$default` stage, API/Cognito and artifact are unchanged. Retain root/commit/input/artifact/binary custody and independently expected review digest. Apply only through the existing reviewed-run flow. The driver verifies selected output identities; immutable-version GetFunction verifies both actual Lambda environments and ZIP hashes. Require `/healthz=200`, `/readyz=503` and unauthenticated CRUD denial before publication. Failed apply/verification is a stop, never a release receipt.
7. Keeping all writers/traffic blocked and cleanup disabled, rerun default read-only recovery verification, then explicitly publish with the **same** prepared run and exact inputs:

   ```sh
   npm run recovery:verify -- --source-config /private/live.json --restored-config /private/restored.json --owner-identities /private/current-owners.json --run-id <uuid> --publish-restored
   ```

   This runs verification again rather than trusting the earlier receipt, requires `GLOBAL/PUBLICATION={published:false,runId:<uuid>}`, saves a bounded verified receipt, and atomically checks its exact bound recovery root while changing that gate to true. It reads the gate back before success. It touches only the restored owner_state gate/receipt. A changed run, interrupted remap, stale/corrupt inventory or gate race fails closed. If an uncertain post-write outcome occurs, inspect the exact gate/run privately before retrying; an already-published gate is not silently adopted. The operator must prevent concurrent writes: strong paginated verification is not a cross-table snapshot.
8. Confirm restored gate/run, stable URL and `/readyz=200`, then perform separately authorized synthetic ownership/CRUD/image checks. Resume ordinary traffic by restoring the previously reviewed `allowed_source_ips` through a fresh application preview/apply only after these checks and the verified application ledger agree; keep `published=true` and Scheduler disabled for this release. Enable Scheduler last through another normal reviewed application preview/apply with the same selection, exact artifact and `published=true`; restore any temporary invocation controls only when safe. Record actual live results separately; local mocks are not acceptance.
9. Before new writes, rollback keeps traffic blocked and Scheduler disabled, conditionally prepares the selected restored gate false if necessary, returns bootstrap `restored_tables={}` first, then platform `{}` and verifies original outputs/grants, then previews/applies application `{}` with the retained exact baseline/artifact. Verify both environments and original publication state before resuming. Do not delete either dataset or original image versions. After any new writes, do not switch to the old snapshot without an explicit reconciliation/data-loss decision and another verified recovery plan. Code-only rollback leaves the selected data unchanged.

## Local interfaces and private progress

`publishRecovery(input, deps)` (explicit fresh-verified publication), `verifyRecovery(input, deps)`, `preserveRecoveryImages(input, deps)`, and `remapRecoveryOwners(input, mapping, deps)` return `RecoveryReport` with `matched`, position-only `missingImages`, `mismatchedOwners`, `countDiscrepancies`, `unresolvedJobs`, `readyToSwitch`, and `cognitoCredentialsRestored: false`. `RecoveryInput` supplies only source/restored `EnvironmentIdentity`, run UUID and confirmed owner identities; no legacy JSON or mapping reread is required.

`createRecoveryStore(client, config, input, imageServices, budget)` binds the restored runtime configuration, effective limits, explicit input and read-only source images/restored images/clock/UUID services. `RecoveryStore` retains gate, prepareUnpublished, publishVerified(runId, report, budget), listItems, listOwners, getJob, replaceImage, remapOwner and saveReport; the targeted additional ports are `listJobs()`, `bindRun(input, mapping, budget)`, `stageImageReplacement(previous, targetOwnerId, runId, budget)`, and read-only `hasIncompleteRemap(runId, budget)`. `remapOwner(from, to, runId, budget)` keeps its four-argument signature. Only explicit operations bind or write run state; verification neither creates a run nor calls saveReport.

All progress lives in the restored owner_state table, outside runtime records. At `GLOBAL/RECOVERY#<runId>`, the root stores `inputSha256 = SHA256(JSON.stringify({ contractVersion: 1, input, limits }))`, nullable `mappingSha256 = SHA256(JSON.stringify(mapping))`, and a nullable bounded report receipt (report hash and numeric counts/readiness only). The first explicit map may bind after an earlier prepare/preserve; a subsequent different map, environment, identity file, limits or run identity cannot resume that run. No private map or whole position array is stored in the root.

`GLOBAL/RECOVERY#<runId>#OWNER#<oldOwnerId>` stores input hash, from/to hashes, `phase` (`preparing`, `copying`, `copied`, `done`), active `itemCount`, `imageBytes`, total `recordCount`, and SHA-256 of ID-sorted original runtime records. `GLOBAL/RECOVERY#<runId>#ITEM#<oldOwnerId>#<SHA256(JSON.stringify(id))>` stores one validated original record and the input hash. `GLOBAL/RECOVERY#<runId>#IMAGE#<hash>` stores one original record, target owner hash, input hash and immutable pending job; its key hash covers JSON `[previous.ownerId, previous.id, previous.thumbnail, targetOwnerId]`. The complete original record binds the prior reference and item fields; the pending job binds the new UUID/key/time and exact shared cleanup keys. The image_jobs row uses only runtime-accepted fields, with no recovery-only attributes. Counters use only the exact runtime `itemCount` and `imageBytes` names.

Roots and owner markers contain counts/hashes, never growing arrays. Item/image intents each hold one runtime-validated record (URL/title/ID limits apply), so aggregate progress can exceed 400 KiB without a single growing DynamoDB row or an aggregate item cap. Synthetic tests exercise 1000 default-limit items with aggregate progress above 400 KiB and enforce a 400 KiB maximum for every individual transport write. Migration chain-v2 roots/chunks and RATE rows are not owner counters and are not parsed as recovery state; recovery does not require the original migration files or reinterpret raw migration pointers.
